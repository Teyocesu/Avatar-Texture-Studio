## Focused follow-up review

**Additional confirmed finding — P1, replacement-failure data loss (corrected).** SafeFileIO formerly called File.Replace with a null backup and deleted the completed temporary file in finally after any exception. [Microsoft's ReplaceFileW failure states](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) document that error 1176 without a backup can leave the destination absent, and error 1177 can rename the old data. Unity's [2022.3 Mono branch](https://github.com/Unity-Technologies/mono/blob/b8eb56fab45dd52845fabba7b7ddc9a80b2b0498/mono/metadata/w32file-win32.c#L468) calls ReplaceFileW; this source pin is not a claim that the unavailable 2022.3.22f1 binary was executed. The null-backup plus unconditional cleanup could discard both old and new recoverable bytes. The helper now requests a unique same-directory backup, deletes that backup only after successful replacement, and on replacement failure keeps recovery files and throws an error naming both paths. It never falls back to deleting the destination. The unchanged public Write call delegates to the actual File.Replace; one internal replacement delegate permits a small filesystem fault-injection regression, not a GPU framework.

The regression first exited **1**, reporting `partial replacement failure retains previous painting bytes`; after correction it exits **0**, checks previous backup bytes, completed new bytes and visible recovery paths, and retains all previous assertions. That run uses injected Win32 failure states on macOS/.NET 8. Successful replacement and cleanup use the real local File.Replace implementation. Native Windows/Unity Mono error 1176/1177, filesystem permissions/locks and crash durability are **NOT TESTED**. API availability was checked against [Unity 2022.3's .NET profiles](https://docs.unity3d.com/2022.3/Documentation/Manual/dotnetProfileSupport.html) and [File.Replace](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=netframework-4.8.1); API availability does not prove identical runtime behavior.
